## 2. 产品定义

### 2.1 产品目标（Product Goals）

1. **正确拆分混轨**：对"同一轨道内低音 riff + 高音旋律并存"的片段，自动把音符分成两个可独立查看/编辑的声部，拆分后两个声部之和 = 原音符全集（不丢音、不重复音）。
2. **安全降级**：当检测置信度不足或不存在分离场景时，保持现有单轨输出不变——**分离是增强，绝不能破坏已经能正常修复的单轨流程**。
3. **语义清晰**：拆分结果在 Guitar Pro 中一眼可辨（哪条是低音、哪条是旋律），且不与现有"voice 2 = 超范围音符"机制互相污染。

### 2.2 成功标准（可度量）

- 在样本 "Tokyo Midnight Highway (Guitar).mid"（2151 音符 / 140 小节）上，系统能**检测出**并**拆出**低音 riff 声部，人工抽查无"旋律音被误分到低音"或"低音音被误分到旋律"的明显错误（抽样 ≥ 95% 正确）。
- 不分离场景（纯旋律 / 纯 riff / 单声部）下，输出与当前版本**完全一致**（回归无损）。
- 拆分后两条 track 在 GP5 中可正常打开、可分别静音与编辑。

### 2.3 用户故事（User Stories）

1. 作为吉他手，我上传一条"低音 riff 和旋律混在一起"的 MIDI，修复后在 Guitar Pro 里能看到 **Lead 轨**和 **Rhythm 轨**两条轨，这样我能分别查看和编辑低音线条与旋律。
2. 作为编曲者，当某小节同时存在低音 riff 和高音旋律时，我希望系统只在这一段拆分，而不要把我的纯旋律段落也硬拆出一条空的低音轨。
3. 作为普通用户，当我上传的 MIDI 本来就只有一条清晰旋律时，我希望输出和以前一样（单轨），而不是被强行拆成两条。
4. 作为进阶用户，我希望看到"哪些小节被拆了、拆分的可信度有多高"，低置信度的地方能有所提示，方便我人工复核。

## 3. 核心产品决策（重点）

### 决策 1：分离粒度 —— 推荐「2 条独立 track」，而非单轨双 voice

| 维度 | 方案 A：单轨双 voice（voice 1=旋律，voice 2=低音 riff） | 方案 B：2 条独立 track（Lead 轨 + Rhythm 轨） |
| --- | --- | --- |
| 与现有 voice 2 的冲突 | **严重冲突**。现有 voice 2 专归"超范围音符"（吉他弹不出的音），若让 voice 2 兼做"低音 riff"，两者语义打架，无法区分 | **无冲突**。每轨内部仍保留 voice 2 = 该轨的超范围音符 |
| GP 里的可读性 | 单轨双声部，符杆方向/颜色区分，不如双轨直观 | 两条轨各自清晰，可分别静音/换音色/编辑，体验最好 |
| 改动量 | 小（只需改 voice 赋值逻辑） | 中（需新增声部分离 stage + AssembleStage 多轨产出 + exporter 多轨导出） |
| IR/数据模型契合度 | 不需要动 IR | **已原生契合**：`GuitarProjectIR.tracks` 本就是 `list[GuitarTrackIR]`，且 `GuitarTrackIR.role` 已预留 lead/rhythm/bass |
| 语义扩展性 | voice 只有 2 个，无法表达"低音+和声+旋律"三声部 | 天然支持未来扩展多声部 |

**推荐：方案 B（2 条独立 track）。** 理由：

1. **voice 2 已被占用**是硬约束——方案 A 会破坏现有的超范围音符机制，得不偿失。
2. IR 数据模型**早就为多轨做好了准备**（`tracks` 是列表、`role` 字段已存在），"改动更大"的代价其实可控：主要工作在 `AssembleStage`（当前硬编码 `tracks=[track]`）和 GP5 exporter。
3. 用户诉求"分别看到/编辑两个声部"在双轨下体验最佳，且角色语义（lead/rhythm）清晰。

> 架构师若评估 P0 工期过紧，可降级为「P0 用 voice 表达、P1 升级为 track」，但需**先做 voice 2 语义迁移设计**（见决策 4），并保留音符的 stream 标签以便后续无缝升级——**不建议直接复用现有 voice 2**。

### 决策 2：检测标准（给方向，具体算法交架构师）

判断"某时刻/某小节存在低音 riff + 高音旋律"的候选信号（可组合使用）：

1. **音高直方图双峰检测**：对检测窗口内所有音符做 pitch 直方图，若出现明显的"低音峰 + 高音峰"双峰分布，且两峰之间存在明显 gap，判定为混合。
2. **复音 onset 同窗**：同一时间窗内，低音区与高音区**同时活跃**（有并发 onset），而非先后交替。
3. **动态分隔点**：不写死音高阈值，用聚类 / 最大间隔（gap）切分得到当前段的 split pitch；参考吉他音域（riff 常落在 E2–D3/G3 低音弦区，旋律在高音区）。
4. **时值/连续性辅助**：低音 riff 常为短时值（八分/十六分）且**节奏重复**；旋律常为较长时值、音高连续移动、多用连音。

**必须输出置信度**：每次分离判断带 `confidence`，供降级与 UI 使用。

### 决策 3：分离范围 —— 推荐「只对检测到的混合片段/小节分离」

- **全曲统一分离**（不推荐）：会把纯旋律段也硬拆出空的低音轨，且纯 riff 段会被误判，产生大量空轨/空小节，体验差。
- **只对混合片段分离**（推荐）：只在检测到"低音 + 高音并存"的片段/小节拆出第二条轨，非混合段保持单轨。与 Steven 描述"某些小节里"一致。
- 注意：低音 riff 常跨多小节连续，拆分后的 Rhythm 轨音符会集中在混合段，其余小节为休止——这是预期行为，需在 UI 上让用户理解。

### 决策 4：与现有 voice 2 的关系 —— 采用 track 分离，voice 2 语义不变

- 保持 `VoiceStage` 现有语义：**voice 2 永远 = 超范围音符（不可弹奏音高）**，不做任何改动。
- 声部分离发生在 **track 层**，不碰 voice：
  - 拆分后产出 **Lead track**（高音旋律，role=lead）与 **Rhythm track**（低音 riff，role=rhythm）。
  - 每条 track 内部仍用 voice 1 = 正常音符、voice 2 = 该轨的超范围音符。
- 这样两条机制正交共存，互不污染。

## 4. 需求池

### P0（必须，本次迭代核心）

- **混合检测**：检测某片段/小节是否存在"低音 riff + 高音旋律"，输出分隔点 + 置信度。
- **音符拆分**：按动态分隔点把音符归入 low / high 两组，保证拆分后并集 = 原音符全集（不丢、不重）。
- **IR 多轨产出**：`AssembleStage` 从单轨改为可产出 2 条 `GuitarTrackIR`（lead/rhythm 角色、命名、tuning 正确）。
- **GP5 多轨导出**：exporter 支持多 `GuitarTrackIR` 导出（含正确的 voice 语义、小节对齐、休止符）。
- **安全降级**：无分离场景或低置信度时，回退单轨，输出与当前版本一致（回归无损）。
- **与 voice 2 共存**：确保新增 track 分离不破坏现有超范围音符 → voice 2 的逻辑。

### P1（应该）

- **前端展示两条轨**：结果/谱面视图展示 Lead 与 Rhythm 两条轨，标注角色。
- **分离置信度展示**：低置信度分离的小节高亮/标记，提示用户复核。
- **分离报告**：记录哪些小节被分离、分隔点音高、置信度（可写入 IR `changes`/`warnings` 或前端展示）。

### P2（可选）

- **声部独立回放**：在预览中单独播放 lead / rhythm 声部。
- **手动调整**：用户手动指定分隔点、或手动把个别音符移到另一轨。

## 5. UI 方向（若涉及前端）

- 结果谱面区展示 **两条轨**（Lead Guitar / Rhythm Guitar），可上下滚动、分别聚焦。
- 拆分出的 Rhythm 轨默认展开，轨名带角色标识（如 "Rhythm (分离)"）。
- **置信度可视化**：低置信度分离的小节用淡色高亮 + 图例说明"此处为自动分离，建议复核"。
- 可选**对比视图**：切换"分离前（单轨）/ 分离后（双轨）"。
- GP5 导出默认包含双轨；无分离时保持单轨导出（对用户无感知变化）。

## 6. 待确认问题（需用户 / 架构师拍板）

1. **低音 riff 音域**：Steven 样本里低音 riff 的实际音域是多少？是否需要按标准吉他 E2 为界的先验，还是完全动态检测？（影响检测准确率）
2. **角色归属**：极低的 riff（接近贝斯音域）应标 `rhythm` 还是 `bass`？是否要引入"低于某音高 → bass"的规则？
3. **降级粒度**：低置信度时是"整曲回退单轨"还是"仅该片段回退单轨"？
4. **声部数量上限**：v2 只做 2 声部（低音 + 旋律），还是需要预留三声部（低音 + 和声 + 旋律）扩展？
5. **手动覆盖是否必须**：P2 的"手动调整"是否必须进本次迭代，还是纯自动 + 人工在 GP 里改？
6. **检测粒度**：按小节检测，还是按时间窗（允许跨小节边界）检测？
7. **track 命名与顺序**：拆分后 Lead 在前还是 Rhythm 在前？命名用 "Lead"/"Rhythm" 还是保留原轨名 + 后缀？
8. **性能预算**：2151 音符 / 140 小节的样本，检测 + 分离耗时上限要求？（是否需在 API 响应内同步完成）
